## 1. 이 저장소에 설정된 것

작업을 시작하기 전에 **이미 걸려 있는 제약**을 알아야 합니다. 모르고 부딪히면 원인을 못 찾습니다.

| 설정 | 내용 | 여러분에게 미치는 영향 |
|------|------|----------------------|
| 기본 브랜치 | `develop` | clone하면 `develop`에서 시작합니다 |
| `main` 보호 | 승인 **2명** + 코드 소유자 승인 필수 | 직접 push 불가. 배포용이라 건드릴 일이 거의 없습니다 |
| `develop` 보호 | 승인 **1명** 필수 | **직접 push 불가.** 반드시 PR을 거쳐야 합니다 |
| Merge 방식 | Squash merge만 허용 | 커밋 여러 개가 하나로 합쳐집니다 |
| 브랜치 자동 삭제 | 켜짐 | 머지되면 작업 브랜치가 자동으로 지워집니다 |
| 비밀값 push 차단 | 켜짐 | API 키가 포함된 커밋은 **push 자체가 거부**됩니다 |
| 대화 해결 필수 | 켜짐 | 리뷰 코멘트를 전부 Resolve해야 머지됩니다 |
| CI | GitHub Actions | PR마다 빌드·검사가 자동 실행됩니다 |

**핵심: `develop`에 직접 push할 수 없습니다.** 모든 변경은 브랜치 → PR → 리뷰 → 머지를 거칩니다.

## 2. 처음 한 번만 하는 설정

### 2-1. 저장소 받아오기

```bash
git clone https://github.com/Team-likelion-2nd-Project/<레포이름>.git
cd <레포이름>
```

`<레포이름>` 은 자기 팀 것으로 바꿉니다. 예: `likelion-2nd-team01`

### 2-2. 내 정보 등록

커밋에 찍힐 이름과 이메일입니다. **GitHub 계정과 같은 이메일**을 쓰세요. 다르면 잔디(기여 그래프)가 안 찍힙니다.

```bash
git config user.name "홍길동"
git config user.email "본인@github이메일.com"
```

GitHub에 이메일을 공개하기 싫으면 노출 없는 주소를 쓸 수 있습니다.

```bash
git config user.email "12345678+깃허브아이디@users.noreply.github.com"
```

이 주소는 GitHub → Settings → Emails 에서 확인합니다.

### 2-3. 확인

```bash
git config user.name
git config user.email
git branch
```

`develop` 이 나오면 정상입니다.

## 3. 작업 한 사이클 전체 흐름

```
이슈 생성  ──►  브랜치 생성  ──►  작업 + 커밋  ──►  PR 생성
                                                      │
                                                      ▼
   이슈 자동 close  ◄──  Squash Merge  ◄──  리뷰 승인 + CI 통과
```

**작업은 항상 이슈에서 시작합니다.** 이슈 없이 브랜치를 만들면 나중에 "이건 왜 만든 거지?"가 됩니다.

## 4. 1단계 — 이슈 만들기

### 4-1. 이슈 템플릿 5종

저장소 → **Issues** 탭 → **New issue** 를 누르면 5개 중에 고릅니다.

| 템플릿 | 언제 쓰나 | 자동 라벨 |
|--------|----------|----------|
| **기능 개발** | 새로 만들 기능 | `feat` |
| **버그 리포트** | 동작하지 않는 문제 | `fix` |
| **트러블슈팅** | 막혔는데 원인을 모를 때 | `help-wanted` |
| **문서 작업** | README, Wiki, API 명세 | `docs` |
| **회의록** | 정기 회의, 회고 | `meeting` |

빈 이슈는 만들 수 없게 막아 뒀습니다. 반드시 템플릿을 씁니다.

### 4-2. 잘 쓴 이슈 vs 못 쓴 이슈

**못 쓴 예**

```
제목: 로그인
내용: 로그인 만들기
```

무엇을 어디까지 만들면 끝인지 아무도 모릅니다.

**잘 쓴 예**

```
제목: [FEAT] 카카오 소셜 로그인 API 구현

작업 내용:
카카오 OAuth2로 로그인하고 우리 서비스 JWT를 발급한다.

세부 작업:
- [ ] 카카오 개발자 앱 등록 및 REST API 키 발급
- [ ] /auth/kakao/callback 엔드포인트 구현
- [ ] 최초 로그인 시 User 레코드 생성
- [ ] JWT 발급 및 응답 반환

완료 조건:
- 카카오 계정으로 로그인하면 accessToken이 응답에 포함된다
- 같은 계정으로 재로그인하면 User가 중복 생성되지 않는다

영역: backend
우선순위: P1
```

**완료 조건은 반드시 검증 가능한 문장으로 씁니다.** "잘 동작한다"가 아니라 "재로그인 시 중복 생성되지 않는다" 처럼요.

### 4-3. 세부 작업 쪼개는 기준

하나가 **2시간을 넘으면 더 쪼갭니다.** 큰 덩어리는 진행 상황이 안 보이고, 리뷰도 어려워집니다.

### 4-4. 이슈 번호 확인

만들고 나면 제목 옆에 `#12` 같은 번호가 붙습니다. **이 번호를 계속 씁니다.** 브랜치명에도, 커밋에도, PR에도요.

## 5. 2단계 — 브랜치 만들기

### 5-1. 최신 상태로 맞추기

**작업 시작 전에 항상 develop을 최신으로 당겨옵니다.** 이걸 건너뛰면 나중에 충돌이 납니다.

```bash
git checkout develop
git pull origin develop
```

### 5-2. 브랜치 생성

```bash
git checkout -b feature/#12-kakao-login
```

### 5-3. 이름 규칙

```
<종류>/#<이슈번호>-<영문-요약>
```

| 종류 | 언제 |
|------|------|
| `feature` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 |
| `refactor` | 리팩터링 |
| `chore` | 설정, 의존성 |

**규칙**

- 요약은 **영어 소문자 + 하이픈**으로 씁니다. 한글이나 공백은 쓰지 않습니다
- 3~5단어 정도로 짧게
- 이슈 번호를 반드시 넣습니다

```
좋은 예
feature/#12-kakao-login
fix/#34-signup-email-validation
docs/#56-update-api-spec

나쁜 예
feature/카카오로그인        (한글)
feature/login              (이슈 번호 없음)
jimin-branch               (개인 이름)
feature/#12-add-kakao-oauth-login-and-jwt-token-issue  (너무 김)
```

## 6. 3단계 — 작업하고 커밋하기

### 6-1. 변경 확인

```bash
git status
git diff
```

### 6-2. 스테이징

```bash
git add 파일명
```

`git add .` 는 편하지만 **의도치 않은 파일까지 올라갑니다.** 특히 `.env`, 키 파일이 위험합니다. 습관적으로 `git status` 로 확인하세요.

### 6-3. 커밋 메시지 규칙

```
<종류>: <한글 요약> (#이슈번호)
```

| 종류 | 용도 |
|------|------|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 수정 |
| `style` | 코드 포맷 (동작 변경 없음) |
| `refactor` | 리팩터링 |
| `test` | 테스트 |
| `chore` | 빌드, 설정, 의존성 |
| `design` | UI, CSS 변경 |

```bash
git commit -m "feat: 카카오 로그인 콜백 엔드포인트 추가 (#12)"
```

**좋은 예**

```
feat: 카카오 로그인 콜백 엔드포인트 추가 (#12)
fix: 회원가입 이메일 중복 검증 오류 수정 (#34)
design: 메인 페이지 카드 레이아웃 반응형 대응 (#56)
```

**나쁜 예**

```
수정                      (뭘 수정했는지 모름)
feat: 여러가지 수정        (구체적이지 않음)
카카오 로그인 추가          (종류 없음, 이슈 번호 없음)
```

### 6-4. 커밋 단위

**한 커밋에는 한 가지 일만 담습니다.** 로그인 기능과 CSS 수정을 한 커밋에 넣으면 나중에 되돌리기 어렵습니다.

### 6-5. push

```bash
git push origin feature/#12-kakao-login
```

처음 push할 때 `-u` 를 붙이면 이후에는 `git push` 만 쳐도 됩니다.

```bash
git push -u origin feature/#12-kakao-login
```

## 7. 4단계 — PR 올리기

### 7-1. PR 생성

push하면 GitHub 저장소 페이지 상단에 **Compare & pull request** 버튼이 뜹니다. 없으면 Pull requests 탭 → New pull request.

**병합 방향을 반드시 확인하세요.**

```
base: develop   ←   compare: feature/#12-kakao-login
```

`base` 가 `main` 으로 되어 있으면 `develop` 으로 바꿉니다. 기본값은 `develop` 이지만 가끔 잘못 잡힙니다.

### 7-2. 제목

커밋 메시지와 같은 형식입니다.

```
feat: 카카오 소셜 로그인 API 구현 (#12)
```

### 7-3. 본문

PR 템플릿이 자동으로 채워집니다. **`Closes #12` 를 반드시 넣으세요.** 이게 있어야 머지될 때 이슈가 자동으로 닫힙니다.

```markdown
## 관련 이슈
Closes #12

## 작업 내용
- 카카오 OAuth2 콜백 엔드포인트 구현
- 최초 로그인 시 User 자동 생성
- JWT 발급 로직 추가

## 리뷰 포인트
- JWT 만료 시간을 1시간으로 했는데 적절한지 의견 부탁드립니다
```

**작업 내용은 커밋 목록 나열이 아니라 리뷰어가 맥락을 이해할 수 있게 씁니다.** 리뷰 포인트에 확신 없는 부분을 적으면 리뷰 품질이 크게 올라갑니다.

### 7-4. Draft PR 활용

작업이 끝나지 않았어도 PR을 먼저 열 수 있습니다. **Create draft pull request** 를 누르세요. 팀원이 진행 상황을 볼 수 있고, 방향이 틀렸을 때 일찍 잡을 수 있습니다.

작업이 끝나면 **Ready for review** 를 누릅니다.

### 7-5. 라벨과 담당자

오른쪽 사이드바에서 지정합니다.

- **Assignees**: 본인
- **Labels**: 종류(`feat`) + 영역(`area/backend`) + 우선순위(`P1`)

## 8. 5단계 — 리뷰하고 머지하기

### 8-1. 머지 조건

`develop` 으로 머지하려면 아래가 전부 충족돼야 합니다.

- [ ] **승인 1명 이상**
- [ ] **CI 통과** (초록 체크)
- [ ] **모든 리뷰 코멘트 Resolve**

`main` 은 승인 2명 + 코드 소유자 승인까지 필요합니다.

### 8-2. 리뷰하는 사람이 지킬 것

- 리뷰 요청 후 **24시간 안에 1차 응답**
- 코멘트에는 **이유와 대안**을 같이 씁니다

```
나쁜 코멘트: 이거 별로인데요
좋은 코멘트: 이 로직이 매 요청마다 DB를 조회해서 N+1이 발생할 것 같습니다.
            fetch join으로 한 번에 가져오면 어떨까요?
```

- 반영이 선택 사항이면 **`nit:`** 을 앞에 붙입니다

```
nit: 변수명을 userList보다 users로 하면 더 읽기 좋을 것 같아요
```

### 8-3. 자기 PR은 자기가 승인할 수 없습니다

GitHub이 막습니다. 반드시 다른 팀원에게 요청하세요.

### 8-4. 머지

**Squash and merge** 만 활성화되어 있습니다. 커밋 여러 개가 하나로 합쳐져서 `develop` 히스토리가 깔끔하게 유지됩니다.

머지하면 자동으로

- 작업 브랜치가 삭제됩니다
- 연결된 이슈(`Closes #12`)가 닫힙니다

### 8-5. 머지 후 정리

로컬에도 반영합니다.

```bash
git checkout develop
git pull origin develop
git branch -d feature/#12-kakao-login
```

## 9. 자주 겪는 문제

### 9-1. push가 거부됩니다

```
! [remote rejected] develop -> develop (protected branch hook declined)
```

**원인**: `develop` 에 직접 push하려 했습니다.
**해결**: 브랜치를 만들어 PR을 올립니다.

```bash
git checkout -b feature/#12-my-work
git push -u origin feature/#12-my-work
```

### 9-2. 비밀값 때문에 push가 막힙니다

```
remote: error: GH013: Repository rule violations found
remote: - Push cannot contain secrets
```

**원인**: API 키나 토큰이 커밋에 들어갔습니다.
**해결**: 그 키는 **이미 노출된 것으로 간주하고 즉시 폐기·재발급하세요.** 커밋을 지워도 안전하지 않습니다.

파일을 추적에서 빼고 다시 커밋합니다.

```bash
git rm --cached 문제파일
echo "문제파일" >> .gitignore
git commit -m "chore: 비밀값 파일 제외 (#번호)"
```

방금 커밋에 들어간 거라면 되돌립니다.

```bash
git reset --soft HEAD~1
```

### 9-3. 충돌(conflict)이 났습니다

PR 화면에 "This branch has conflicts" 가 뜹니다.

```bash
git checkout develop
git pull origin develop
git checkout feature/#12-my-work
git merge develop
```

충돌 파일을 열면 이런 표시가 있습니다.

```
<<<<<<< HEAD
내 코드
=======
develop의 코드
>>>>>>> develop
```

**둘 중 무엇을 남길지 직접 판단해서** `<<<<<<<`, `=======`, `>>>>>>>` 표시를 전부 지우고 정리합니다. 애매하면 상대 코드를 쓴 팀원에게 물어보세요.

```bash
git add .
git commit -m "chore: develop 병합 충돌 해결 (#12)"
git push
```

### 9-4. 커밋 메시지를 잘못 썼습니다

아직 push 전이라면:

```bash
git commit --amend -m "feat: 올바른 메시지 (#12)"
```

이미 push했다면 그냥 두세요. Squash merge 때 PR 제목으로 합쳐지므로 큰 문제가 아닙니다.

### 9-5. 엉뚱한 브랜치에서 작업했습니다

`develop` 에서 커밋해버린 경우:

```bash
git branch feature/#12-my-work
git reset --hard origin/develop
git checkout feature/#12-my-work
```

`git reset --hard` 는 **되돌릴 수 없습니다.** 위 순서대로 브랜치를 먼저 만든 뒤 실행하세요.

### 9-6. CI가 빨간 X입니다

PR 하단 **Details** 를 눌러 로그를 봅니다. 빨간 단계를 펼치면 원인이 나옵니다.

`Secret Scan` 이 실패했다면 `.env` 파일이 커밋된 것입니다. 9-2를 참고하세요.

## 10. 절대 하면 안 되는 것

| 금지 | 이유 |
|------|------|
| `main` / `develop` 직접 push | 보호 규칙으로 막혀 있고, 리뷰 없는 코드가 들어갑니다 |
| `.env` 커밋 | 비밀값 유출. `.env.example` 만 커밋합니다 |
| API 키·비밀번호·인증서 커밋 | **이 저장소는 공개입니다.** 전 세계가 볼 수 있습니다 |
| `git push --force` | 팀원 작업이 사라집니다 |
| 이슈 없이 PR만 생성 | 왜 한 작업인지 추적이 안 됩니다 |
| 자기 PR 자기가 approve | GitHub이 막습니다 |
| 대용량 파일 커밋 | 저장소가 무거워집니다. Git LFS를 씁니다 |

**이 저장소는 공개(public)입니다.** 커밋하기 전에 항상 `git status` 로 무엇이 올라가는지 확인하세요.

## 11. 팀 시작 전 체크리스트

프로젝트를 시작하기 전에 팀에서 **딱 한 번** 해야 하는 일입니다.

### 11-1. CODEOWNERS 채우기 (가장 급함)

`.github/CODEOWNERS` 에 `{{팀장-id}}` 같은 자리 표시자가 남아 있습니다. **이걸 안 채우면 `main` PR에서 리뷰어 자동 할당이 동작하지 않습니다.**

```
*                       @팀장깃허브아이디
/frontend/              @프론트1 @프론트2
/backend/               @백엔드1 @백엔드2
/.github/workflows/     @팀장깃허브아이디
```

### 11-2. README 채우기

`README.md` 의 `{{...}}` 부분을 전부 바꿉니다. 남은 게 있는지 확인:

```bash
grep -rn "{{" README.md
```

특히 중요한 세 항목입니다.

- **빠른 심사 흐름(5분)** — 심사위원이 5분 안에 핵심을 볼 수 있는 순서
- **Core Design** — 기능 나열이 아니라 **설계 판단**
- **범위 경계** — 되는 것과 안 되는 것. 여기서 과장하면 질의응답에서 무너집니다

### 11-3. CI 워크플로 정리

`.github/workflows/ci.yml` 에서 **안 쓰는 job을 지웁니다.** 프론트만 있으면 `backend` job을 삭제하세요.

폴더가 없으면 자동으로 건너뛰게 되어 있어 당장 실패하지는 않습니다.

### 11-4. Wiki 페이지 만들기

Wiki 탭에서 아래 페이지를 미리 만들어 둡니다. 문서를 나중에 몰아서 쓰면 반드시 부실해집니다.

```
Home / 기획 배경 / User Flows / UI Screens
Architecture / ERD / API Specification
배포 가이드 / 회의록 / 트러블슈팅
```

### 11-5. Projects 보드 연결

조직 Projects 보드에 이 저장소를 연결하고 컬럼을 만듭니다.

```
Backlog → To Do → In Progress → In Review → Done
```

### 11-6. 주 1회 회의록 남기기

**회의록 이슈 템플릿**으로 매주 기록을 남기세요. 발표 자료를 만들 때 이게 전부 근거가 됩니다. 특히 **결정 사항**과 **액션 아이템(담당자 + 기한)** 은 빠뜨리지 마세요.

결정되지 않은 것은 "보류"라고 적습니다. **추측해서 적지 않습니다.**
